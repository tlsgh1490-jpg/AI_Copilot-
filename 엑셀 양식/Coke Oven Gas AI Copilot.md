# Coke Oven Gas AI Copilot
## 최종 기획안

### 1. 과제 목표

Coke Oven Gas 단일 라인을 대상으로 공정 엔지니어가 주요 KPI를 모니터링하고, 이상 발생 시 주요 영향 변수·예상 원인·점검 후보를 확인하며, 계약 기준 대비 실적과 원가 영향을 빠르게 파악할 수 있는 **AI Copilot MVP**를 구현한다.

AI가 실제 원인을 확정하거나 운전을 대신하는 것이 아니라,

**정량 분석결과를 현업 사용자가 빠르게 이해하고 판단할 수 있도록 지원하는 것**

을 목적으로 한다.

---

## 2. 문제 정의

현재 공정 상태 및 이상을 분석하려면 주요 KPI, 관련 변수, 공정 관계, 계약 기준, 관리범위 및 원가 영향을 각각 확인해야 한다.

본 과제에서는 다음 업무 흐름을 하나로 연결한다.

**KPI 상태 확인  
→ 이상 후보 탐지  
→ 주요 영향 변수  
→ 예상 원인 및 점검 후보  
→ 계약 기준/관리범위 비교  
→ 원가 영향  
→ AI 자동 분석·설명**

---

## 3. 시스템 설계 원칙

LLM이 공정 Raw 데이터를 직접 계산하거나 이상 여부를 판단하지 않는다.

전체 구조는 다음과 같다.

**공정 데이터  
→ Python 분석엔진  
→ 계약/원가 분석  
→ 구조화된 분석결과  
→ DB 캐시  
→ 필요 시 LLM API  
→ Copilot/UI**

### Python 역할

- KPI 계산
- 조업일 집계
- 정상 기준 계산
- 규칙 기반 이상탐지
- 주요 영향 변수 분석
- 계약 기준 비교
- 관리범위 판정
- 절감/초과량 및 원가 계산
- 선택적 ML 이상점수 계산

### LLM 역할

- Morning Brief 생성
- 이상 이벤트 분석결과 자연어 설명
- 계약·원가 분석결과 자연어 설명

즉,

**정량 계산은 Python, 설명은 LLM**

으로 역할을 분리한다.

## 4. 데이터 보안 및 합성데이터 전략

실제 공정 Raw 데이터는 외부 구현 환경에서 직접 사용하지 않는다.

실제 데이터는 사내 환경에서 분석하고 다음과 같은 특성만 활용한다.

- 분포형태
- 왜도
- 변동성
- 값 변화속도
- 상관계수
- 관계 방향
- 관계 강도
- 시간지연
- 현업 판단
- 현업 신뢰도

실제 태그명·설비명은 가명 처리한다.

실제 날짜, Raw 행 데이터, 실제 계약값, 실제 단가 등은 사용하지 않는다.

상관계수만으로 원본 시계열을 역산할 수는 없지만, 상관관계 역시 공정정보이므로 필요 시 발표·외부 공유 단계에서는 `강함/중간/약함` 등의 범주형 정보로 추가 축약할 수 있다.

본 과제에서 사용하는 방식은 Z-score 표준화나 Min-Max 정규화와 다르다.

Z-score나 정규화는 **기존 데이터의 스케일을 변환하는 전처리 방식**이며, 본 과제는 Raw 데이터를 직접 사용하지 않고 실제 데이터에서 추출한 특성과 현업 지식을 이용해 **새로운 합성 시계열을 생성하는 방식**이다.

## 6. KPI·변수 및 변수관계

### KPI 목록

KPI 자체의 정보와 관리기준을 관리한다.

- KPI ID
- KPI명
- 단위
- 산식/산출근거
- 정상/경고/이상 기준
- 관리 방향

### 변수 목록

공정 변수의 기본 정보를 관리한다.

일부 KPI가 다른 KPI 또는 변수에 영향을 주는 경우 KPI와 변수 역할을 동시에 가질 수 있다.

### 변수통계

별도 시트에서 관리한다.

- 왜도
- 분포형태
- 분포 비대칭
- CV
- 변동성
- 변화속도

### 변수관계

모든 공정 영향관계를 별도 관계표에서 관리한다.

관계 유형:

- 변수 → 변수
- 변수 → KPI
- KPI → 변수
- KPI → KPI

관리정보:

- 상관계수
- 관계 방향
- 관계 강도
- 시간지연
- 판단근거
- 신뢰도

단순 상관계수만으로 관계를 판단하지 않는다.

일 단위 집계, 다른 운전조건, 시간지연 등으로 상관계수가 낮더라도 현업상 중요한 관계는 유지할 수 있다.

신뢰도는 통계적 유의성이 아니라 **현업에서 해당 공정관계가 존재한다고 판단하는 확신 수준**을 의미한다.

## 8. 이상 시나리오

대표 이상 시나리오 약 **3~5개**를 정의한다.

기본 흐름:

**정상 → 이상 전조 → 이상 발생 → 조치 → 회복**

각 시나리오는 다음 정보를 포함한다.

- 이상 유형
- 주요 선행 변수
- 전조 변화 방향
- 영향 KPI
- 시간지연
- 예상 원인 후보
- 점검 후보
- 조치 또는 정상화 조건
- 회복 패턴

시나리오는 실제 과거이력 DB를 만드는 목적이 아니라:

- 합성데이터 이상구간 생성
- 이상탐지 검증
- QA
- UI 데모
- Copilot 자동 분석

을 위한 **정답이 있는 테스트 케이스**로 활용한다.

무작위 이상치를 넣는 대신 현업적으로 의미 있는 흐름을 삽입한다.

## 9. 더미데이터 QA

2년치 전체 데이터를 사람이 직접 검토하지 않는다.

Python 기반 자동 QA를 수행한다.

### 자동 검증

- 시간 누락
- 중복
- 결측
- 비정상 값
- KPI 산식 일치
- 변수관계 방향
- 이상 이벤트 정상 삽입 여부
- 시간지연
- 전조 → 이상 → 조치 → 회복 순서
- 07:00~익일 07:00 조업일 집계

QA 결과:

**PASS / REVIEW / FAIL**

### 현업 검토

현업은 전체 데이터를 확인하지 않고:

- 정상 대표구간
- 시나리오별 대표 이벤트 1~2건
- REVIEW / FAIL 구간

만 그래프로 확인한다.

확인 항목:

- 변화 방향의 현실성
- 변화폭의 적정성
- 선후관계
- 시간지연
- 회복 속도

QA 과정에서 발견되는 수정사항은 최종 발표에서 시행착오 및 피드백 반영 사례로 활용한다.

## 10. 계약 기준 데이터

공정 합성데이터 생성 및 QA 완료 후 별도로 생성한다.

이번 MVP에서는 경영계획과 계약을 분리하지 않고 **계약 기준으로 통합**한다.

계약 데이터는 공정 시간단위 데이터에 직접 섞지 않고 기간별 별도 테이블로 관리한다.

주요 항목:

- 계약 기준 ID
- 적용기간
- KPI ID
- 계약 기준값
- 관리 하한
- 관리 상한
- WARNING 기준
- ABNORMAL 기준
- 단위
- 가상 단가 또는 원가지수

공정 데이터 수준을 참고하여 비현실적인 계약기준이 생성되지 않도록 한다.

## 11. 계약 관리범위

단순 계약 달성률만 제시하지 않고 관리범위를 함께 적용한다.

### 상태

**NORMAL**
- 관리범위 내

**WARNING**
- 관리범위 접근 또는 단기 이탈

**ABNORMAL**
- 관리범위 큰 폭 이탈 또는 지속 이탈

분석 흐름:

**공정 실적  
→ 계약 기준 비교  
→ 관리범위 판정  
→ 계약 대비 차이  
→ 절감/초과량  
→ 원가 영향**

## 12. 원가 및 절감효과

실제 회사 단가나 실제 계약금액은 사용하지 않는다.

가상 단가 또는 기준지수 100을 사용한다.

예:

**기준 Steam 사용량  
= 실제 생산량 × 계약 Steam 원단위**

**절감량  
= 기준 사용량 - 실제 사용량**

**가상 절감금액  
= 절감량 × 가상 단가**

원가 분석은 단순 이상 손실금액보다 **계약 기준 대비 운영 효율의 절감/초과 효과**를 중심으로 한다.

## 15. LLM API 및 DB 캐싱

전체 Raw 데이터를 LLM에 직접 전달하지 않는다.

**Raw 데이터  
→ Python 분석  
→ 구조화된 요약결과  
→ LLM**

구조를 사용한다.

Morning Brief나 동일 이상분석처럼 결과가 반복되는 경우 매번 LLM을 호출하지 않는다.

### 최초 생성

DB 확인  
→ 결과 없음  
→ LLM 호출  
→ 응답 저장

### 재조회

DB 확인  
→ 기존 응답 반환  
→ LLM 미호출

주요 캐싱 대상:

- Morning Brief
- 일별 이상분석
- 월간 계약 실적
- 원가 요약
- 확정 이상 이벤트 분석

## 19. MVP 제외 및 향후 확장

### 과거 유사사례 추천

실제 정비·이상 이력 DB가 없는 상태에서 합성 시나리오만으로 추천 기능을 구현할 경우 실제 활용성을 과장할 수 있어 MVP에서 제외한다.

## 20. 과제의 핵심 문제해결 과정

본 과제의 핵심은 단순 AI 기능 구현보다 다음 판단 과정에 있다.

**실제 Raw 데이터 활용 제약  
→ 일 단위 통계/관계분석**

**시간단위 데이터 활용 필요  
→ 2년 시간단위 합성데이터 생성**

**50여 개 관계 수작업 문제  
→ Excel 자동 상관분석**

**상관계수만으로 판단 어려움  
→ 통계 + 현업판단 결합**

**합성데이터의 현실성 문제  
→ 이상시나리오 + QA**

**계획·계약 구조 복잡  
→ 계약 기준으로 통합**

**단순 달성률 부족  
→ 관리범위 추가**

**LLM에 모든 계산 위임 문제  
→ Python + LLM 역할분리**

**반복 LLM 비용  
→ DB 캐싱 및 API 비용관리**

**데이터 근거 부족 기능  
→ 유사사례·자유질의는 향후 확장으로 이동**
